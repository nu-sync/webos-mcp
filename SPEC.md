# webos-mcp MVP specification

Status: proposed, November 3, 2026. This document defines an initial implementation; it is not evidence that the server exists or that the TV supports every proposed operation.

## Outcome

Let an MCP-capable assistant operate a supported LG webOS TV through a persistent, task-scoped connection: connect, inspect a fresh screen, send a small remote action, inspect the result, and disconnect. The assistant retains responsibility for deciding what to do and interpreting the result. An action acknowledgement is not proof that the desired screen appeared.

The initial target is one user-selected LG webOS TV on the local network, operated by one MCP client at a time. macOS, Windows, and Linux are target platforms; support is established by platform testing, not by the choice of language. The TV is shared; a request to connect does not authorize waking it, changing inputs, launching apps, or sending buttons. User intent supplies authorization for individual actions. Do not make changes to the TV's installed software, startup, network settings, or privacy configuration.

## Architecture

Implement a local Rust MCP server with the official [Rust MCP SDK (`rmcp`)](https://github.com/modelcontextprotocol/rust-sdk), Tokio, and the SDK's stdio transport. The MCP client starts the server process; the TV session is an independent application lifecycle inside it. The process starts disconnected and does not contact the TV until `tv_connect` is called. No network listener, TV-side daemon, MCP task extension, or built-in LLM is needed for the MVP.

The session owns its paired remote control and button-input connections and, when needed, the SSH connection and tunnel for the selected screenshot backend. Reuse those connections between calls. No private network address, device name, account, key path, machine-specific trace, or other personal identifier belongs in source, examples, or public evidence.

Control and visual capture are separate capabilities. The ordinary webOS remote pairing path does not require root. A screenshot API used by some community servers is undocumented and its availability varies by model and firmware; probe it rather than promise support. A rooted compositor-over-SSH backend is an optional explicitly configured path, with trusted host-key verification and user-provided existing SSH authentication. Do not root TVs, enable SSH, install Developer Mode, or install TV-side software as an onboarding side effect. LG Developer Mode is a distinct, time-limited developer workflow, not a substitute for persistent root access. The [webOS compositor documentation](https://www.webosose.org/docs/reference/ls2-api/com-webos-surfacemanager/) says video layers may be absent.

If the TV has no verified screenshot backend, report `visual_capture_unavailable`; do not pretend visual navigation works. Because this MVP requires a fresh observation before actions, unsupported capture means this visual-control journey is unavailable, even if pairing and connection succeed. Support for a TV and its host platform must be established by tests; the only prior live demonstration was on one rooted device.

## Onboarding and persistent credentials

Provide a separate interactive `webos-mcp setup` command. The MCP stdio server must not prompt or write human-oriented output to stdout. MCP client-mediated onboarding is future work unless the client supports a tested interactive flow. Onboarding must:

1. Ask for a TV host or discover candidates, confirm the selected device with the user, and use the TV's own pairing prompt. No network scanning without the user's request. Discovery is optional; manual host entry must work.
2. Complete the webOS pairing handshake once, store the issued client key in the OS credential store, and retain only non-secret device configuration locally. On later server starts, reuse the stored key without requesting pairing again while it remains valid; report revoked or unavailable credentials and guide the user through re-pairing. Pairing grants remote-control authority, so treat the key as a secret.
3. Probe and report visual capture capability. If the user chooses the optional rooted-SSH backend, configure an existing hostname, SSH user, port and key/agent reference; confirm the host key through a trusted out-of-band fingerprint, reject unknown or changed keys until the user explicitly verifies them, and preserve host-key checking on every connection. Never silently alter the TV. The exact key reference and target host are user-specific local configuration, not checked-in defaults. Do not copy SSH private keys or persist passphrases.
4. Run a connection and one-shot screenshot check when supported, explain capture limitations, then close setup-owned connections. Capture may create transient TV files; clean only files owned by setup and report cleanup failures. Provide explicit commands to inspect the saved non-secret configuration, re-pair and remove a device; remove its local credential on user request. Document that local removal and TV-side authorization revocation are separate operations.

Use a cross-platform credential-store abstraction backed by macOS Keychain, Windows Credential Manager, and a Linux Secret Service-compatible keyring where available. Confirm the chosen Rust backend's behavior and persistence on each target; Linux headless environments may lack an unlocked store. If secure persistence is unavailable, fail persistent setup clearly and offer a session-only option that pairs and retains the key in memory in the same running server process; after that process exits it requires pairing again. This option needs a tested interactive flow or a direct in-process handoff; a separate setup process cannot provide an in-memory key to a later process without a secure transfer. Do not silently fall back to plaintext. If a future encrypted-file option is offered, design and review its encryption and key management separately. Never send pairing keys, passwords, SSH private keys, or credential-store contents to an MCP client, model, logs, test fixtures, or repository. Operating-system keyrings may still require unlock or user approval; the server cannot guarantee no future prompts, or preserve a TV authorization after revocation or reset.

Prefer local stdio, verified SSH host keys, and the TV's authenticated TLS connection where supported. For self-signed TV certificates, use an explicit user-verified trust-on-first-use or certificate pinning policy, persist the verified fingerprint, and reject unexpected changes; do not silently disable certificate verification. Confirm the actual LG protocol and certificate behavior on representative devices before claiming support. If a direct screenshot endpoint returns a URL, restrict requests and redirects to the confirmed TV endpoint, enforce scheme, size and time limits, and validate returned image bytes to avoid treating an untrusted URL as permission to fetch arbitrary resources.

## MCP tools

Tools use typed JSON inputs. The server returns errors as tool failures with actionable, non-secret messages. Exact Rust types are implementation details, but the semantics below are required.

| Tool | Input | Success | State and effects |
| --- | --- | --- | --- |
| `tv_connect` | `{}` | Connection status, visual capability, and TV power if available. | From disconnected, establish the session. Repeated calls when connected report the existing session without opening another. Never wake the TV. Connection failure cleans partially created resources. |
| `tv_observe` | `{}` | MCP image content containing the fresh frame, plus capture time and current app if known. | Allowed while connected, including after an action timeout. Return only an image captured by this call; never return an old image as a new one. A failed capture requires another successful observation before actions. |
| `tv_press` | `{ "button": "RIGHT", "count": 2 }` | Button and count sent, and delivery status. | Allowed only with a successful observation since the last action. `count` defaults to 1 and is bounded to 1–5; the server paces individual presses. Supported buttons: `UP`, `DOWN`, `LEFT`, `RIGHT`, `ENTER`, `BACK`, `HOME`. A batch is one action for the lifecycle and requires another observation afterward. |
| `tv_launch` | `{ "app_id": "example.app" }` | Launch request acknowledgement. | Allowed only with a successful observation since the last action. Launch is an action and requires another observation. An acknowledgement does not establish which screen opened. |
| `tv_disconnect` | `{}` | Disconnected or already disconnected. | Stop accepting actions, close only task-owned resources, and leave the MCP server running. Repeated calls are safe. |

`tv_launch` takes an app ID known from configuration or prior inventory; this MVP does not invent IDs or promise an app-listing tool. Adding discovery is a separate API decision. `tv_press` supports bounded repetition only: it does not infer focus, decide whether a sequence is safe, or guarantee each press moved selection. Examples specify names and semantics, not a promise of a particular SDK version or generated JSON schema.

A screenshot result is an MCP image content block with the correct MIME type, alongside concise metadata. It represents what the compositor captured, not necessarily every layer on the physical panel. By default keep frame bytes in memory, don't write screenshots to logs, and retain no image history. Data sent to a remote model leaves the laptop; local transport between server and TV does not change that fact.

## Lifecycle contract

The source of truth for the proposed high-level TV-session transitions is [`statechart/TvSession.tla`](statechart/TvSession.tla), with the reader-facing [chart](statechart/chart.mmd), [configuration](statechart/TvSession.cfg), and [model limitations](statechart/README.md). The chart distinguishes disconnected, connecting, fresh view needed, observing, ready with fresh view, acting, uncertain, closing, server shutdown cleanup, and stopped.

Implement the lifecycle as an explicit Rust enum with state-owned resources and exhaustive transitions, rather than independent flags. A single session owner serializes calls that affect the TV. Validate tool inputs at the MCP boundary. Concurrent or invalid calls must return a clear busy or invalid-state error; they must not queue a stale button action to run later. In particular, a `tv_press` or `tv_launch` requires Ready and changes it to Acting before external I/O. Every acknowledged action invalidates the previous observation and returns to Fresh view needed. `tv_observe` does not launch an app or press a button.

Connection setup, active operations, disconnect, and graceful server shutdown must follow the matching model transitions. A disconnect or shutdown during an in-flight operation must prevent late completions from reviving the old session or overwriting a newer state. Cleanup must target only resources owned by this server. A failure to confirm cleanup must be reported; the implementation must not claim disconnected resources were released merely because cleanup was requested.

### Timeout and late delivery: implementation gate

The current model permits Uncertain → Observing → Ready, but explicitly assumes the timed-out action cannot take effect after that recovery observation. That assumption has **not** been established for LG's remote input socket. A fresh image by itself does not establish that no delayed key press remains in flight.

Before an implementation relies on that transition, demonstrate and document a transport-level ordering or termination guarantee on the actual path, including a fault-injection test for late delivery. Otherwise, keep the session unable to send further actions after an uncertain delivery until a recovery procedure establishes the action can no longer take effect. Update the TLA+ model, chart, and tests to represent the chosen recovery procedure before shipping. Closing and reopening a connection is not, by itself, proof that a TV-side command already queued cannot execute. Never automatically retry an uncertain action.

The current statechart does not model onboarding, credential storage, capability negotiation, host-key verification, or multi-process ownership. Before implementing those lifecycle transitions, extend the model or add a separate checked onboarding model; define how incomplete setup and credential revocation recover. The statechart is an abstract design contract, not code generation or proof of the Rust implementation. Any added transition, batching behavior, session recovery, or changed lifecycle policy requires updating the model and checking the implementation against it. Re-run TLC after model changes. If runtime behavior cannot conform to a modeled assumption, fix the assumption or model rather than declaring conformance.

## Verification and acceptance

1. **Model:** Re-run the command in [statechart/README.md](statechart/README.md); all declared invariants and deadlock checks pass, with no unchecked rules. The current checked model is a baseline, not proof of unmodeled timing or cleanup behavior.
2. **Lifecycle tests:** Exercise the actual session owner through connect, observe, act, observe, disconnect, reconnect, and graceful shutdown. Verify state guards, duplicate connect/disconnect, failed connect cleanup, capture failure, timeout uncertainty, in-flight disconnect, shutdown, and late completion. Verify screenshot failure cannot surface a previous frame as fresh. Use a controllable fake transport to test ordering and failure, and explicitly label it simulated.
3. **MCP integration:** Launch the actual compiled server through stdio with an MCP client; verify tool discovery, schemas, image content and MIME type, errors, and clean EOF shutdown. Confirm stdout contains only MCP protocol messages; send diagnostics to stderr. Do not assume a particular client displays images without checking it.
4. **Real TV:** With a requested, authorized navigation journey and a supported TV awake, establish a starting screenshot, connect once, use multiple button calls over the same session, inspect resulting screenshots, and disconnect. Verify the selected destination on screen and verify only this server's connections and tunnel closed. Do not alter TV startup or install a TV-side service. Report untested apps, playback and capture layers.
5. **Onboarding and portability:** On macOS, Windows and Linux, test setup, secure persistence across process restart, reconnect without repeat pairing, user-initiated removal and re-pairing, unavailable or locked credential stores, interrupted setup, and changed host/certificate identity. Use fake stores and devices in automated tests and label those simulations; document actual OS/TV combinations tested. Verify no secrets or real device identifiers occur in fixtures, logs, generated reports or repository files. Test the unsupported-screenshot path and the optional SSH path separately. Do not require access to a rooted TV for ordinary pairing.
6. **Performance:** Record connect, button, capture, model/tool round-trip, and end-to-end journey timings, plus success, failures and retries. Compare at least five matched runs of the existing helpers and the persistent candidate, alternating order and reporting median and range. The 2–3× end-to-end speedup is an exploration target, not a release claim or substitute for reliability. If model-inference timing is unavailable, report transport and end-to-end measurements separately and name that gap.

## Out of scope

Continuous video, audio capture, waking or powering off the TV, purchases, app installation, settings changes, simultaneous multi-TV control, LAN-hosted HTTP, automatic focus recognition, model selection, and autonomous navigation planning. A later feature may propose any of these with its own contract and verification.

## Public repository hygiene

Before the first public push, inspect every file intended for publication, generated output, Git-tracked content, and any commit history that will be pushed. Exclude real IP addresses, hostnames, user names, local absolute paths, pairing keys, SSH material, screenshots containing household information, device identifiers, and logs with environment details. Use synthetic fixtures and placeholders; never record real screenshots or credentials in tests. Add ignore rules for local device config, credential stores, screenshots and runtime output before implementing storage. Review staged changes and the repository history with a secret scanner as an aid, not as proof of absence. If a credential has ever entered a commit, revoke or rotate it and address history separately before publication; removing it from the current file is not enough. This specification does not itself publish or authorize a GitHub push.
