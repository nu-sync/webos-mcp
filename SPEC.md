# webos-mcp MVP specification

Status: implementation contract, updated November 6, 2026. The local Rust server implements the six tools below. Live-device, portability, and performance claims are limited to the evidence in [verification status](docs/verification.md).

## Outcome

Let an MCP-capable assistant operate a supported LG webOS TV through a persistent, task-scoped connection: connect, inspect a fresh screen, send a small remote action, inspect the result, and disconnect. The assistant retains responsibility for deciding what to do and interpreting the result. An action acknowledgement is not proof that the desired screen appeared.

The initial target is one user-selected LG webOS TV on the local network, operated by one MCP client at a time. macOS, Windows, and Linux are target platforms; support is established by platform testing, not by the choice of language. The TV is shared; a request to connect does not authorize waking it, changing inputs, launching apps, or sending buttons. User intent supplies authorization for individual actions. Do not make changes to the TV's installed software, startup, network settings, or privacy configuration.

## Architecture

Implement a local Rust MCP server with the official [Rust MCP SDK (`rmcp`)](https://github.com/modelcontextprotocol/rust-sdk), Tokio, and the SDK's stdio transport. The MCP client starts the server process; the TV session is an independent application lifecycle inside it. The process starts disconnected and does not contact the TV until `tv_connect` is called. No network listener, TV-side daemon, MCP task extension, or built-in LLM is needed for the MVP.

The session owns its paired remote control and button-input connections and, when needed, the SSH connection and tunnel for the selected screenshot backend. Reuse those connections between calls and maintain them with bounded, non-action keepalives while connected. No private network address, device name, account, key path, machine-specific trace, or other personal identifier belongs in source, examples, or public evidence.

Control and visual capture are separate capabilities. The ordinary webOS remote pairing path does not require root. A screenshot API used by some community servers is undocumented and its availability varies by model and firmware; probe it rather than promise support. A rooted compositor-over-SSH backend is an optional explicitly configured path, with trusted host-key verification and user-provided existing SSH authentication. Do not root TVs, enable SSH, install Developer Mode, or install TV-side software as an onboarding side effect. LG Developer Mode is a distinct, time-limited developer workflow, not a substitute for persistent root access. The [webOS compositor documentation](https://www.webosose.org/docs/reference/ls2-api/com-webos-surfacemanager/) says video layers may be absent.

If the TV has no verified screenshot backend, report `visual_capture_unavailable`; do not pretend visual navigation works. Because this MVP requires a fresh observation before actions, unsupported capture means this visual-control journey is unavailable, even if pairing and connection succeed. Support for a TV and its host platform must be established by tests; the only prior live demonstration was on one rooted device.

## Lessons from the prototype

The following observations come from one local prototype and are test cases for the MVP, not compatibility guarantees for every TV or application:

- The tested remote protocol used a control connection and a separately negotiated button-input socket. Treat them as distinct session resources; exercise partial connection failures, reconnection, and cleanup for each. Do not assume an input socket remains valid after the control session changes.
- A rooted compositor capture returned recognizable application interfaces, but its output may omit video or HDMI layers. Validate the complete image and return the result only after this request succeeds; never substitute a previous frame. Clean temporary capture artifacts owned by the request and report unconfirmed cleanup.
- One capture command exited without a reply when its standard input closed early; keeping input open until the reply worked on the tested TV. If an SSH subprocess backend is used, test its input lifetime, bounded timeout, output handling, and cleanup rather than relying on shell behavior across platforms.
- TV apps can use their own keyboards. A text-entry API acknowledged input without changing the visible field in one tested app. Text entry is outside the MVP; if added later, require visual verification and do not interpret an acknowledgement as proof of visible text.
- A timed-out request can leave delivery uncertain. Preserve the distinction between failure before sending and a timeout after sending, and follow the late-delivery gate below. When allocating a local tunnel port, avoid assuming a released probe socket reserves that port; handle bind conflicts without disrupting another process.

## Onboarding and persistent credentials

Provide a separate interactive `webos-mcp setup` command. The MCP stdio server must not prompt or write human-oriented output to stdout. MCP client-mediated onboarding is future work unless the client supports a tested interactive flow. Onboarding should ask only for information needed by the selected path and give clear progress, success, and recovery messages. Treat the chosen address as sensitive: save it in the OS credential store by default; an explicitly chosen local-file option may store it unencrypted in a private user directory. Never put it in process arguments, logs, MCP output, or checked-in files; if it changes, let the user update it without repeating pairing unless authorization is no longer valid. Onboarding must:

1. Ask the user to enter the TV IP address or hostname, explain where to find it in the TV network settings, and use the TV's own pairing prompt. Do not discover devices, scan IP ranges, or scan ports. Connect only to the specified host and the configured webOS remote port; use the protocol default unless the user explicitly supplies an override. A direct connection attempt or capability request to that endpoint is not a scan.
2. Complete the webOS pairing handshake once and store the issued client key in the explicitly selected credential store. On later server starts, reuse the stored key without requesting pairing again while it remains valid; report revoked or unavailable credentials and guide the user through re-pairing. Pairing grants remote-control authority, so treat the key as a secret.
3. Check and report visual capture capability using only the selected device and explicitly configured endpoints; do not search for SSH or try a range of ports. If the user chooses the optional rooted-SSH backend, configure an existing hostname, SSH user, port and key/agent reference; confirm the host key through a trusted out-of-band fingerprint, reject unknown or changed keys until the user explicitly verifies them, and preserve host-key checking on every connection. Never silently alter the TV. The exact key reference and target host are user-specific local configuration, not checked-in defaults. Do not copy SSH private keys or persist passphrases.
4. Run a connection and one-shot screenshot check when supported, explain capture limitations, then close setup-owned connections. Capture may create transient TV files; clean only files owned by setup and report cleanup failures. Provide explicit commands to inspect the saved non-secret configuration, re-pair and remove a device; remove its local credential on user request. Document that local removal and TV-side authorization revocation are separate operations.

Use a cross-platform credential-store abstraction backed by macOS Keychain, Windows Credential Manager, and a Linux Secret Service-compatible keyring where available. Confirm the chosen Rust backend's behavior and persistence on each target; Linux headless environments may lack an unlocked store. If secure persistence is unavailable, fail persistent setup clearly and offer a session-only option that pairs and retains the key in memory in the same running server process; after that process exits it requires pairing again. This option needs a tested interactive flow or a direct in-process handoff; a separate setup process cannot provide an in-memory key to a later process without a secure transfer. Do not silently fall back to plaintext. A user may explicitly choose an unencrypted local credential file, understanding that filesystem permissions, backups, and other local processes affect access. Store it outside the repository, restrict permissions where supported, write it atomically, reject invalid or exposed files, and do not send its contents to an MCP client. Linux and Windows permission behavior must be verified separately. If a future encrypted-file option is offered, design and review its encryption and key management separately. Never send pairing keys, passwords, SSH private keys, or credential-store contents to an MCP client, model, logs, test fixtures, or repository. Operating-system keyrings may still require unlock or user approval; the server cannot guarantee no future prompts, or preserve a TV authorization after revocation or reset.

Prefer local stdio, verified SSH host keys, and the TV's authenticated TLS connection where supported. For self-signed TV certificates, use an explicit user-verified trust-on-first-use or certificate pinning policy, persist the verified fingerprint, and reject unexpected changes; do not silently disable certificate verification. Confirm the actual LG protocol and certificate behavior on representative devices before claiming support. If a direct screenshot endpoint returns a URL, restrict requests and redirects to the confirmed TV endpoint, enforce scheme, size and time limits, and validate returned image bytes to avoid treating an untrusted URL as permission to fetch arbitrary resources.

## MCP tools

Tools use typed JSON inputs. The server returns errors as tool failures with actionable, non-secret messages. Exact Rust types are implementation details, but the semantics below are required.

| Tool | Input | Result | State and effects |
| --- | --- | --- | --- |
| `tv_connect` | `{}` | Connection and visual-capability status. | Establish the session without waking the TV. Repeated calls check the existing connection. Failed setup retains owned cleanup state until disconnect; no scan is performed. |
| `tv_observe` | Optional `wait_ms`, `change_timeout_ms`. | Fresh MCP image plus a new `observation_id`, visual-change classification, dimensions, timing, recovery, and unresolved-delivery metadata. | Allowed while connected, including when delivery is unresolved. A failed observation invalidates prior action authority and returns no old image. |
| `tv_press` | Required `button`, `observation_id`; optional `count`, `observe`, `wait_ms`, `change_timeout_ms`. | Separate delivery and observation results; a new image and ID by default. | Requires the latest observation ID. `count` defaults to 1 and is bounded to 1–5, with paced presses. Supported buttons: `UP`, `DOWN`, `LEFT`, `RIGHT`, `ENTER`, `BACK`, `HOME`. A batch consumes one observation ID. |
| `tv_launch` | Required `app_id`, `observation_id`; optional `observe`, `wait_ms`, `change_timeout_ms`. | Separate delivery and observation results; a new image and ID by default. | Requires the latest observation ID. Launch consumes that ID; transport success does not establish the visible app. |
| `tv_disconnect` | `{}` | Confirmed disconnection, already disconnected, or an explicit cleanup error. | Stop accepting actions and close owned resources. Failed or cancelled cleanup remains in `Closing` and blocks actions and reconnect. Repeated disconnect attempts never conceal unresolved cleanup. |
| `tv_metrics` | `{}` | Aggregate operation and stage statistics for the current server process. | Read-only and available in every live server state, including disconnected. No TV I/O or counter reset. |

`observe` defaults to `true` on action calls. With `observe: false`, the caller must obtain a new observation before the next action. Standalone observation defaults to `wait_ms: 0` and `change_timeout_ms: 0`; an action's observation defaults to 250 ms and 1000 ms. The permitted ranges are 0–5000 ms and 0–3000 ms respectively. The change timeout is a window for starting follow-up captures, not a wall-clock operation deadline. Stop sampling when a frame differs from the prior observation, is black, has no baseline, the window expires, or four samples have been collected. An in-flight capture retains its own timeout and may finish after the sampling window.

`visual_change` is `first`, `changed`, `unchanged`, or `black`, based on decoded image pixels and the last returned frame. It does not recognize focus or prove that an action caused a change. `ui_settled` is always `unknown`. The response reports its return timestamp, not the TV's physical frame timestamp. Keep images in memory and return only a frame from the current call.

`delivery: sent` means local transport success, not proof of TV application. A send error reports `delivery: unknown` and keeps the durable guard. A rejection before any send reports `not_sent`. If sending succeeds but capture fails, return `delivery: sent`, an `observation_error`, and no image or observation ID. The caller must not repeat an action because its observation failed. Recovery never replays a button or launch request.

`tv_launch` takes an app ID known from configuration or prior inventory; this MVP does not invent IDs or promise an app-listing tool. Adding discovery is a separate API decision. `tv_press` supports bounded repetition only: it does not infer focus, decide whether a sequence is safe, or guarantee each press moved selection. Examples specify names and semantics, not a promise of a particular SDK version or generated JSON schema.

A screenshot result is an MCP image content block with the correct MIME type, alongside concise metadata. It represents what the compositor captured, not necessarily every layer on the physical panel. By default keep frame bytes in memory, don't write screenshots to logs, and retain no image history. Data sent to a remote model leaves the laptop; local transport between server and TV does not change that fact.

## Local metrics

Collect bounded, aggregate timing and outcome statistics in memory by default. `tv_metrics` returns a snapshot scoped to the current server process; counters begin at process start and are discarded at process exit. It does not count its own calls, return individual events, or alter session state; relative to the TV session model it is a stuttering step. Empty statistics include a zero count and `null` for unavailable durations. A read must not block on TV I/O or wait for an action to complete; in-flight operations appear only when finalized.

Measure elapsed time using a monotonic clock for each completed `tv_connect`, `tv_observe`, `tv_press`, `tv_launch`, and `tv_disconnect` call, including failed, timed-out, and cooperatively cancelled calls; forced process termination can lose in-flight measurements. Use mutually exclusive outcomes `success`, `failure`, `timeout`, and `cancelled` so they sum to the completed count. For each operation and fixed stage, report count, outcome counts, total, minimum, maximum, and mean elapsed milliseconds. A dropped in-flight measurement is finalized once as cancelled. Validation failures inside a tool handler count as failures; typed JSON or protocol rejections before handler entry are excluded. Optional or uninstrumented stages have zero samples. Counters stop accepting samples when saturated; overflowing timing sums become `null`, and the snapshot exposes saturation rather than wrapping. Label aggregate statistics with their process lifetime and measurement unit.

Current instrumentation covers credential lookup, control and input connection setup, registration, action preflight, command delivery, capture request, image transfer, image validation, and cleanup. The `input_connection` stage measures checks of existing connections before an action; initial handshakes use `connection_setup`. Image transfer includes waiting for remote capture output. A combined action includes observation time in its operation duration and records capture stages under that action. Capture recovery records connection setup and cleanup stages, without a separate recovery counter. Optional or uninstrumented work can leave a stage with zero samples; this does not establish zero cost. A stage is not an operation acknowledgement or proof of visible success. Durations include waiting and are not necessarily CPU time. Parent and child intervals may overlap; do not add them as independent costs. Metrics cannot measure LLM inference or client-side delay unless the client measures those separately. Do not infer a bottleneck from an unverified stage or a small sample.

Metrics use fixed allowlisted operation and stage names, outcome categories, durations, and counts only. Do not collect screen images or text, titles, app IDs, button names or sequences, device addresses, credentials, raw errors, request payloads, or arbitrary labels. No telemetry export, persistent metrics files, background metrics polling, or network listener is enabled by default. Connection keepalives do not collect metrics. A requesting MCP client receives the aggregate, which may reveal usage patterns and may leave the user's machine if forwarded to a model. Set `WEBOS_MCP_METRICS=0` at process start to disable collection; the tool reports disabled collection and zero samples without changing TV behavior. No reset operation or detailed trace is required in the MVP.

Verify metrics against a controllable fake transport with injected stage delays, errors, timeouts, cancellation and skipped stages. Check exact counts, monotonic elapsed-time bounds, disjoint outcomes, zero-sample behavior, privacy allowlists, and snapshot behavior during in-flight operations. Compare enabled and disabled collection for unchanged visible session behavior and measure instrumentation overhead; report the baseline and spread rather than asserting a fixed threshold. Verify MCP schema and response through the actual compiled stdio server. A real-TV run requires appropriate authorization and remains separate from simulated evidence.

## Lifecycle contract

The high-level TV-session model is [`statechart/TvSession.tla`](statechart/TvSession.tla), with the reader-facing [chart](statechart/chart.mmd), [configuration](statechart/TvSession.cfg), and [model limitations](statechart/README.md). The chart distinguishes disconnected, connecting, fresh view needed, observing, ready with fresh view, acting, uncertain, closing, server shutdown cleanup, and stopped. The [observation model](statechart/Observation.tla) adds observation IDs, combined action-observation results, recovery, and retained cleanup uncertainty; see its [report](statechart/observation-report.md). Both models abstract transport behavior and require implementation tests.

Implement the lifecycle as an explicit Rust enum with state-owned resources and exhaustive transitions, rather than independent flags. A single session owner serializes calls that affect the TV. Validate tool inputs at the MCP boundary. Concurrent user calls must return a clear busy error; they must not queue a stale button action to run later. The active request may wait for an internal keepalive, then revalidate connection health and observation identity. Invalid requests fail before delivery. A `tv_press` or `tv_launch` requires Ready and the latest successful observation ID from the current session. It consumes that ID and checks the selected connection before sending; if that check fails or is cancelled, it sends no action and requires a new observation. Before sending an action it durably marks delivery as potentially pending. A preflight does not settle earlier uncertainty and cannot guarantee delivery after it completes. Local send completion invalidates the previous observation. The default combined call then captures a new frame before granting a new observation ID; if capture fails, another observation is required. `tv_observe` does not launch an app or press a button.

Connection setup, active operations, disconnect, and graceful server shutdown must follow the matching model transitions. Closing state retains resource ownership through awaits, errors, and cancellation; only confirmed cleanup reports a clean disconnection. A disconnect or shutdown during an in-flight operation must prevent late completions from reviving the old session or overwriting a newer state. Cleanup must target only resources owned by this server. A failure to confirm cleanup must be reported; the implementation must not claim disconnected resources were released merely because cleanup was requested.

Typed capture failures distinguish connection and channel-open failures from request, transfer, image validation, size-limit, timeout, and cleanup errors. When channel opening fails before any remote capture command starts, close the old SSH connection; if closure is confirmed, the same observation may establish one new trusted connection and retry capture once. A second channel-open failure returns an error. Failures or cancellation with unconfirmed remote cleanup block capture recovery and remain visible during disconnect. Never retry a button or clear unresolved delivery as part of capture recovery. Invalid-image failures return no previous image and do not imply a transport reconnect is needed.

### Timeout and late delivery: implementation gate

The session model blocks further actions while a timed-out or interrupted action is unresolved, even after a screenshot, disconnect, or reconnect. An abstract `DeliverySettled` event represents reliable evidence that the old action cannot take effect later. No such transport guarantee has yet been established. A screenshot or a reopened connection alone is insufficient; never automatically retry an uncertain action. Until a reliable mechanism is verified, keep actions blocked and report the uncertainty.

The session model includes an abstract durable action marker and crash transition. Before relying on recovery after a crash or forced stop, establish that the marker is committed before delivery, survives interruption, and is cleared only on a justified acknowledgement. The onboarding model abstracts secure storage, identity verification and capability checks; it does not yet represent session-only credentials or multi-process ownership. Extend it before implementing behavior that depends on those cases. Neither model proves the Rust implementation or the actual TV transport. Update models and rerun TLC when changing lifecycle behavior.

## Verification and acceptance

1. **Model:** Re-run the command in [statechart/README.md](statechart/README.md); all declared invariants and deadlock checks pass, with no unchecked rules. The current checked model is a baseline, not proof of unmodeled timing or cleanup behavior.
2. **Lifecycle tests:** Exercise the actual session owner through connect, observe, act, observe, disconnect, reconnect, and graceful shutdown. Verify state guards, duplicate connect/disconnect, failed connect cleanup, capture failure, timeout uncertainty, in-flight disconnect, shutdown, and late completion. Verify screenshot failure cannot surface a previous frame as fresh. Use a controllable fake transport to test ordering and failure, and explicitly label it simulated.
3. **MCP integration:** Verify `tv_metrics` is read-only, privacy-safe, and available while disconnected; launch the actual compiled server through stdio with an MCP client; verify tool discovery, schemas, image content and MIME type, errors, and clean EOF shutdown. Confirm stdout contains only MCP protocol messages; send diagnostics to stderr. Do not assume a particular client displays images without checking it.
4. **Real TV:** With a requested, authorized navigation journey and a supported TV awake, establish a starting screenshot, connect once, use multiple button calls over the same session, inspect resulting screenshots, and disconnect. Verify the selected destination on screen and verify only this server's connections and tunnel closed. Do not alter TV startup or install a TV-side service. Report untested apps, playback and capture layers.
5. **Onboarding and portability:** On macOS, Windows and Linux, test setup, secure persistence across process restart, reconnect without repeat pairing, user-initiated removal and re-pairing, unavailable or locked credential stores, interrupted setup, and changed host/certificate identity. Use fake stores and devices in automated tests and label those simulations; document actual OS/TV combinations tested. Verify no secrets or real device identifiers occur in fixtures, logs, generated reports or repository files. Test the unsupported-screenshot path and the optional SSH path separately. Do not require access to a rooted TV for ordinary pairing.
6. **Performance:** Record connect, button, capture, model/tool round-trip, and end-to-end journey timings, plus success, failures and retries. Compare at least five matched runs of the existing helpers and the persistent candidate, alternating order and reporting median and range. The 2–3× end-to-end speedup is an exploration target, not a release claim or substitute for reliability. If model-inference timing is unavailable, report transport and end-to-end measurements separately and name that gap.

## Out of scope

Network discovery, IP or port scanning, continuous video, audio capture, waking or powering off the TV, purchases, app installation, settings changes, simultaneous multi-TV control, LAN-hosted HTTP, automatic focus recognition, model selection, and autonomous navigation planning. A later feature may propose any of these with its own contract and verification.

## Public repository hygiene

Before the first public push, inspect every file intended for publication, generated output, Git-tracked content, and any commit history that will be pushed. Exclude real IP addresses, hostnames, user names, local absolute paths, pairing keys, SSH material, screenshots containing household information, device identifiers, and logs with environment details. Use synthetic fixtures and placeholders; never record real screenshots or credentials in tests. Add ignore rules for local device config, credential stores, screenshots and runtime output before implementing storage. Review staged changes and the repository history with a secret scanner as an aid, not as proof of absence. If a credential has ever entered a commit, revoke or rotate it and address history separately before publication; removing it from the current file is not enough. This specification does not itself publish or authorize a GitHub push.
