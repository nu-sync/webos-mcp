# Verification status

## Faster capture — November 8, 2026

On the configured rooted TV and macOS, five alternating captures of the same Home screen per optimized binary returned full-resolution PNGs through the MCP. The native-PNG baseline median was 1.64 seconds (1.60–1.67 seconds); JPEG capture decoded and encoded as PNG on the host had a 0.28-second median (0.27–0.28 seconds). These are MCP observation timings after connecting, excluding model reasoning; clients connected and disconnected between samples. The capture images were visually inspected, and all ten calls succeeded. On the TV, five native-PNG captures took 1.39–1.49 seconds versus 0.10–0.11 seconds for JPEG, establishing compositor image generation as the main difference for this screen. Results will vary with screen content and device. JPEG is lossy; `WEBOS_MCP_LOSSLESS=1` requests native PNG instead.

The optimized server also connected and captured with the lossless setting, and an actual Home, Left, Right journey returned fresh images and a confirmed disconnect. The returned images showed the focus move and return, though the wallpaper had not yet loaded. JPEG support and fallback behavior on other TVs have not been tested.

## Reliability increment — November 6, 2026

The combined MCP action/observation API, required observation IDs, bounded pixel-change sampling, typed capture recovery, retained cleanup state, and local aggregate metrics are implemented. Current automated validation passes 71 tests: 27 library tests, 35 binary/session tests, five local pinned-transport tests, and four compiled-server MCP tests. `cargo fmt --check` and strict all-target Clippy pass. Optional credential-store and TV tests remain excluded from the default suite.

The session tests exercise stale and previous-session tokens, cancelled preflight/send/observation/disconnect, send success followed by capture failure without replay, persistent uncertainty, cleanup failure, bounded sampling, and concurrent-call rejection. Capture tests cover bounded reconnect, explicit cleanup after authentication failure, failed cleanup, cancellation, image validity, decoded-pixel fingerprints, and stage timing outcomes. Ordinary refused control connections can be closed and retried; cancelled handshakes retain uncertainty. These are implementation tests with synthetic devices or loopback endpoints, not real-TV fault injection.

TLC checked 432 states and 859 steps in the observation model; all eight invariants and deadlock checks passed. Four negative controls detect stale-frame acceptance, previous-session acceptance, replay after capture failure, and false cleanup confirmation. The model abstracts real time, physical remote input, durability, transport semantics and most platform behavior; see the [model report](../statechart/observation-report.md).

On the configured rooted TV and macOS, the compiled debug server reused the private credential file and returned native 1920×1080 PNGs. Manual inspection verified RIGHT then LEFT moved launcher focus and returned it to the starting app. The combined calls took 2.39 and 2.49 seconds, including the default 250 ms wait but excluding model reasoning. Reusing the previous observation ID was rejected as `not_sent`; subsequent use of the current ID succeeded. Disconnect was confirmed. A second opt-in Rust MCP journey passed in 8.15 seconds, excluding final teardown: connect, duplicate connect, observe, combined Home, stale-ID rejection, combined Left, and metrics assertions. Home selected the first launcher app; Left remained at the boundary. Protocol success alone does not establish visible movement. Screenshots are private and outside this repository.

The first live metrics sample attributed about 1.6 seconds to capture/transfer and 0.4 seconds to debug-build PNG validation; command delivery was below a millisecond. Capture/transfer includes compositor execution and waiting for the remote command to exit, so this does not isolate network throughput. These few samples identify where to investigate, not a general benchmark or a 2–3× speedup claim.

A repeatable debug-build comparison ran five alternating trials per candidate on the same launcher menu and persistent connection. Each trial sent Right then Left, with the same 250 ms wait and 1000 ms sampling window. Separate action/observe calls had a median two-button RPC time of 4.947 s (range 4.933–5.015 s); combined calls had a median of 4.998 s (4.972–5.109 s). All ten pairs completed, all 20 result images reported changed pixels, and cleanup succeeded. Sampled first/last trial images visibly moved focus to the adjacent app and back. The combined API halves MCP calls from four to two per pair; the raw measured latency did not improve. The comparison excludes LLM reasoning and client-side image validation/writes; it does not compare against the old one-shot Python helper or establish performance across apps.

The first optimized-build benchmark stopped after three completed pairs: a background keepalive held the same lock that user requests tried to acquire immediately, so the next action and explicit disconnect were rejected as busy. The action was not sent and the durable marker remained clear. A separate shared request gate now rejects overlapping user calls while allowing the active request to wait for a bounded keepalive; it validates health and the observation ID after that wait. Two regressions cover contention, cancellation while waiting, and failed-health invalidation. Restoring the old immediate state-lock rejection makes the contention regression fail. The first failed run is excluded from complete-trial latency claims.

After that fix, the optimized-build comparison completed all ten pairs and confirmed cleanup. Split RPC time was median 4.094 s per two-button pair (range 2.991–4.164 s); combined time was 4.175 s (4.153–4.350 s), or about 2.1 s per action plus screenshot. In combined calls, mean image validation was 42.9 ms and capture/transfer 1756.1 ms. Debug and optimized builds ran sequentially, with the keepalive fix added between them, so this is diagnostic evidence rather than a controlled build-speedup ratio. It supports using the optimized binary and investigating capture/transfer next; it does not show a 2–3× complete agent-loop improvement. All result captures reported changed pixels; sampled final-pair images visibly moved focus and returned it.

A CPU-only debug microbenchmark ran five alternating 50,000-sample batches per mode: enabled aggregation averaged 129.5 ns/sample (per-batch range 128.2–130.4 ns), disabled averaged 13.7 ns (13.2–15.8 ns). It checks one operation timer without concurrent writers, snapshots, TV work, or LLM time; those numbers are not a production overhead guarantee.

The **Model the Domain** principle led to explicit observation authority and retained closing state. **Fix Root Causes** separated known failed connection setup from interrupted setup instead of hiding cleanup errors. **Explain the Number** led to matched alternating trials, phase timings, and separate transport/model latency claims. **Prove It Works** led to compiled MCP tests, implementation fault injection, and real screenshot inspection alongside the model.

## Earlier evidence and remaining platform gaps

On one rooted TV and macOS, an `rmcp` client launched the compiled server, connected with a certificate verified through an existing trusted SSH connection, captured a PNG, sent Home, captured again, sent Left, captured again, and disconnected. Visual inspection confirmed that Home opened the launcher and Left moved its focus. The server rejected a second press until a fresh observation. A later server process reused a newly issued authorization from the OS credential store. These observations establish the tested journey on one TV, not broad compatibility.

The first setup attempt without an existing authorization timed out. A later `setup --re-pair` obtained and stored an authorization with no client key supplied; no TV-side prompt was visually confirmed. The setup process also reused the address and checked SSH capture. The testing initially imported a pre-existing authorization from the user's earlier local prototype; no real credentials, addresses, images, or device identifiers are included here.

Local automated checks cover MCP discovery, disconnected validation and EOF; synthetic registration responses; certificate pin match and mismatch; and complete versus truncated PNGs. An opt-in macOS test wrote a synthetic address to a unique Keychain entry, read it in another process, and removed it. TLC checked the session model including a durable marker and crash transition; its negative control detected unsafe late-delivery recovery. The model assumes durable writes and valid acknowledgement semantics and does not prove the implementation or the TV's transport.

A later state review found that setup could change a standalone saved address before authenticating the TV, leaving it inconsistent with the paired credential. Setup now commits the verified address and credential together; simulated tests cover failed authentication, changed identity, and a successful update. The address model also covers an unconfirmed write, which can leave either the previous or new record in the store. SSH disconnect now waits for the local SSH session to finish; a simulated timeout test checks that it reports unconfirmed cleanup. Neither change has been exercised on the real TV yet.

After the earlier live journey, the non-secret pending-action marker was moved from Keychain to a durable local state file to reduce access prompts. The updated server completed the two-action MCP journey twice on the real TV, including marker migration, fresh images between actions, the stale-observation guard, and disconnect. Visual inspection confirmed the launcher focus moved. The user reported two Keychain password prompts during the second run. Unit tests exercise marker migration and fail-closed handling using a temporary directory. A later change attempts to migrate a legacy separate address into the protected credential entry on connection, so future connections need one protected entry lookup. Its first live attempt timed out waiting for the credential store; the migration has only passed simulated tests. OS unlock and access prompts can still occur; the server cannot observe whether a user sees them.

Remaining verification includes first-time onboarding from a clean store, crash durability across platforms, revocation, multiple independent processes with different local data directories, Windows and Linux credential stores and SSH agents, unsupported screenshot paths, launch, and protected video or HDMI capture. The reliability increment above adds simulated lifecycle/cancellation checks and aggregate metrics. Screenshot capture requires the explicitly configured rooted SSH backend; no discovery or port scanning is performed. The optional private live tests require a configured device and intentional invocation.

A live capture comparison produced all-black frames through both the persistent Rust SSH connection and the separate OpenSSH-based capture. The cause of the black frames remains unverified. The Rust MCP response reports `all_black` from decoded pixels; a live black frame produced `true`. On a later static YouTube home screen, the two capture methods returned byte-identical nonblack PNGs and the Rust response reported `false`. A live MCP observation, right press, observation, left press, observation, and right press returned focus to the starting item, followed by a confirmed disconnect. This flag is a visual cue, not a diagnosis or proof of what appears on the panel. A complete search and channel-navigation journey remains to be verified.

A later live MCP journey dismissed a screensaver, opened YouTube search, entered two letters, selected a suggested query, and visually verified the search results and selected channel. After selecting the channel, the capture channel failed and disconnect could not confirm remote cleanup; a direct capture then returned black. The destination was not visually verified. Some captures immediately after an action preceded the visible change, so a successful capture is not proof that the UI has settled.

The observation model checks that a capture failure or recovery cannot clear unresolved delivery. An intentionally unsafe recovery transition produced the expected counterexample. A later real MCP observation with a requested one-second wait returned after 1.53 seconds, reported `ui_settled: unknown`, and disconnected successfully; the captured frame was black, so this does not verify visual settling. The current reliability increment exercises injected channel-open failure, cleanup interruption, and uncertain delivery against the implementation; those failures have not been deliberately injected on a live TV. The optional wait is a caller choice, not a measured settling threshold.

Run `cargo fmt --check`, `cargo test`, and `cargo clippy --all-targets -- -D warnings` for local checks that do not access the real credential store or TV. Run `cargo test --test native_store synthetic_address_survives_process_restart -- --ignored` only when an OS credential-store test is wanted; it may trigger an OS prompt and creates a unique synthetic entry.

The user explicitly selected the unencrypted private-file option. The server imported an existing authorization over private stdin, verified the TV certificate against a fingerprint obtained via trusted SSH, and then saved the record outside the repository. On macOS, the local file had owner-only permissions. A real MCP journey using that file completed two actions and fresh screenshots; the stale-view guard and disconnect succeeded, and visual inspection confirmed focus moved. After storage-selection hardening, a subsequent real connect/disconnect succeeded. The user confirmed that the final private-file journey showed no password or Keychain prompts. Normal operation on this configured file path does not call Keychain. Windows ACL behavior, clean-install local-file onboarding, other TV models, and the generic import flow remain unverified. The original system credential entries were retained.

A later authorized navigation attempt encountered an uncertain button delivery after a period of inactivity. A subsequent observation through the MCP session failed and disconnect reported unconfirmed cleanup. The session left its durable uncertainty marker in place; no further MCP actions were attempted. An independent read-only capture succeeded, but cannot establish that the earlier button could not arrive late. The requested destination was not reached.

Following the uncertain Home press, action preflight was added to check WebSocket liveness before marking and sending a new action. Simulated tests cover a closed socket, a mismatched old pong, a successful reply, and cancellation; a read-only test confirmed that the tested TV responds to a preflight ping. TLC checked the added preflight state and a negative control detected a premature pending marker. The earlier uncertain action remains blocked and is not cleared by preflight, screenshot, reconnect, or elapsed time. Whether the original failure was caused by idle timeout is not established; the complete journey has not been repeated after this change.

On a later read-only real-TV test, the input socket without keepalives failed a ping after 50 seconds idle. With WebSocket and SSH keepalives enabled, the MCP session captured before and after 50 seconds idle, passed an input/control connection check, and disconnected. The prior unresolved delivery marker remained set. This confirms the observed idle scenario on one TV, not that all disconnections or late actions are solved.

A read-only connect to the configured TV over a remote private network timed out once after the 10-second connection budget; a later retry with no change on the TV took 0.62 seconds. The cause was not established because the single budget covered TCP, TLS, and the WebSocket handshake together. Connection setup now records `tcp_connect`, `tls_handshake`, and `websocket_handshake` stages under `tv_connect`, keeps the same overall budget, and names the stalled step in a timeout that states nothing was sent. Simulated tests cover a refused endpoint, a peer silent after TCP accept, a peer that stalls after TLS, and a cancelled handshake. The opt-in `live_connect_stages` test connects, reports these stage timings, and disconnects without any TV action; one warm optimized-build run connected in 0.75 seconds with confirmed cleanup.

A failed `tv_connect` previously left the session in `Closing`, so a caller had to disconnect before retrying even when nothing had been sent. A setup that runs to a known failure now closes its own resources and returns to disconnected only when that cleanup is confirmed; a cancelled setup or unconfirmed cleanup still remains in `Closing`. This matches the existing `ConnectFailed` transition in `TvSession.tla`, so the model was not changed or rerun. Simulated session tests cover confirmed cleanup, failed cleanup, cancellation during cleanup, and successful setup. The path through the compiled server with a real failed connection has not been exercised.
